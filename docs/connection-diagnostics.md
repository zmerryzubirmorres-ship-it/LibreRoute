# Диагностика подключения FluxonAndroid

Обновление 24.09.2026: ядро `vyandex` теперь обновляет авторизацию до истечения
срока токена и по ответам HTTP 401/403. При успешном обновлении не требуется
перезапускать VPN или заново импортировать профиль. Если Яндекс снова выдаст
CAPTCHA, клиент открывает существующий WebView. При ошибке ручной авторизации
(например, `auth/initial` 401/403 или отсутствии `client-config`) клиент
предлагает открыть WebView; событие сохраняется до возврата приложения на
экран. После успешной проверки и сохранения cookies клиент принудительно
перезапускает текущий туннель, даже если старое ядро ещё числится запущенным.
Сетевые тайм-ауты и единичный HTTP 409 не вызывают WebView. Повторные
приглашения ограничены интервалом пять минут.
Статус «Работает» по-прежнему зависит от сквозной HTTPS-проверки, а не от
одного успешного обновления авторизации.

Приложение различает запущенный нативный транспорт и подтверждённую сквозную
связь. Сообщение `WebSocket connected` или живой процесс означают только
подключение к облачному сервису, а не работающий туннель до выходного узла.

После старта и переподключения статус — «Проверка сквозной связи…». Android
отправляет HTTPS-запрос через локальный SOCKS5 нативного ядра; только успешный
ответ меняет статус на «Работает». При ошибке показывается «Нет сквозной
связи». Проверка повторяется каждые 30 секунд, а разовый ручной запрос не
отменяет периодическую задачу. После смены физической сети статус не
восстанавливается только по факту появления сети: сначала требуется успешная
сквозная проба.

Отрицательный результат означает, что сквозной доступ **не подтверждён**.
Причиной могут быть клиент, документ, выходной узел, его маршрут или сами
контрольные сайты. Чтобы различать «второй узел жив» и «Интернет за ним
доступен», нужен отдельный нативный ping/pong через основной документ.

Старое ядро `libp1npplydtransport.so` доступно только как готовый бинарник.
Новый `libopenflux_client.so` для `arm64-v8a` собирается из соседнего OpenFlux:
он принимает TUN-дескриптор от `VpnService`, обслуживает TCP и DNS (UDP/53
преобразует в DNS-over-TCP через выходной узел), а также поднимает локальный
SOCKS5 для проверки HTTPS. Другой UDP и IPv6 пока не поддерживаются и не
пускаются напрямую. SOCKS5-имена разрешаются через выходной узел, а не DNS
телефона.

Новый бинарник содержит `OFHP`, но `--peer-health` можно включать только в
отдельном тестовом профиле, одновременно на клиенте и выходном узле, с общим
файлом ключа. Старый установленный APK по-прежнему не отвечает на эти кадры.
Общий секрет остаётся в локальном файле; публиковать его или производные
сессионные ключи в документ нельзя.

Первый live-запуск `Fluxon Dev` 24.09.2026 выявил Android-ограничение:
OpenFlux завершался при инициализации политики назначений с ошибкой
`net.InterfaceAddrs(): permission denied`. Код создавал эту политику и для
клиента, хотя она используется только на выходном узле. Инициализация
ограничена ролью exit. После этой правки Go-ядро прошло запуск и приняло TUN,
но транспорт остановился раньше передачи данных: сборка без CGO использовала
Go DNS resolver, который попытался обратиться к `::1:53` и не смог разрешить
имя облачного сервиса на Android. DNS, транспорт и HTTPS через туннель поэтому
не подтверждены.

Для следующего прогона подготовлена arm64-сборка с Android NDK и
`CGO_ENABLED=1`, чтобы DNS использовал системный Android resolver. Ядро успешно
собрано установленным в Android SDK NDK 30.0.16248370; debug APK пересобран и
установлен поверх отдельного пакета `Fluxon Dev`, не затрагивая обычный Fluxon.
Скрипт [`../build-openflux-core.ps1`](../build-openflux-core.ps1) уже проверен
этой сборкой. В live-тесте `Test` ядро дошло до авторизации `vyandex`, но
Яндекс перенаправил запрос на страницу CAPTCHA, где нет ожидаемого скрипта
`client-config`. Нативный процесс вышел с кодом 1; последующая ошибка передачи
TUN FD — следствие его завершения. Приложение вернулось в состояние «Нажмите
для подключения». Android DNS больше не является наблюдаемым блокером, но
транспорт и сквозная HTTPS-проба не подтверждены. Полные URL и параметры
CAPTCHA не должны попадать в журналы и документацию.

Пока не перенесены DoH, доменные правила и SOCKS-аутентификация старого ядра:
профили с этими параметрами новый клиент отклоняет, не выдавая ложный статус.
Из списка `--urls` используется один документ; ротация возможна только после
перезапуска процесса. До успешного повторного запуска NDK-сборки нельзя считать
прохождение трафика, DNS и HTTPS на телефоне подтверждённым.

См. [общий журнал работ](../../README.md) и
[описание протокола OpenFlux](../../OpenFlux/docs/session-diagnostics.md).

## Ручная проверка Яндекса, 24.09.2026

Исходный установленный Fluxon проверен на мобильной сети с профилями `Test`,
`Yandex` и `Yandex2`: каждый получил CAPTCHA до WebSocket. `Fluxon Dev` теперь
распознаёт эту ошибку без вывода URL с токеном, открывает исходный документ в
WebView для решения пользователем и принимает результат только после появления
`client-config`. Cookies и User-Agent передаются ядру через файл в приватной
директории приложения; файл не содержит ключ шифрования OpenFlux и не выводится
в журналы. Ядро поддерживает этот файл для `yandex` и `vyandex`.

После live-проверки `Test` авторизация и WebSocket прошли, но сквозная
HTTPS-проба через SOCKS5 повторно получила тайм-аут. В статистике `vyandex`
зафиксирована отправка без входящих пакетов. Поэтому статус остаётся «Нет
сквозной связи», VPN после теста остановлен. Причину отсутствия ответа нужно
исследовать на клиенте и удалённом узле до развёртывания OpenFlux на VDS89.
Решение CAPTCHA может истечь или оказаться привязанным к сети/браузерному
отпечатку; экран проверки не гарантирует последующее прохождение Go-запросов.

## Тестирование транспорта Google Docs, 24.09.2026

В клиент добавлена поддержка транспорта Google Docs (`TransportType.gdocs` / `googledocs`)
с отдельной векторной иконкой, выбором в интерфейсе и защитой маршрутизации к `docs.google.com:443`.

При live-тестировании профиля `VDS89 Google Docs`:
1. Нативный клиент успешно запускается и перехватывает TCP-пакеты, упаковывая их в теги `<<<C2S:<seq>:<payload>>>>`.
2. Запрос проверки доступности `CONNECT cp.cloudflare.com:443` (и фоллбэки `gstatic`, `firefox`)
   получает таймаут (2500 мс).
3. Причина: метод отправки `publishTag` при отсутствии вебхука Google Apps Script (`--gdocs-webhook`)
   не имеет сетевого пути для анонимной записи в Google Docs и отбрасывает пакеты.
4. Выходной узел на VDS89 опрашивает Google Docs stream, но не получает входящих тегов.
5. Для перехода статуса в «Работает» и отображения задержки требуется развертывание скрипта
   `relay.gs` в документе и передача полученного URL вебхука в параметры туннеля.
