# Контроль команд управления клиент ↔ сервер

Дата: 15 октября 2026 года.

## Порядок выполнения

1. Определяются целевой сервер и операция. Проверяется локальный подписанный допуск:
   срок действия, роль и scope для выбранного сервера.
2. Запрашивается свежий `get-cluster-snapshot` тем же административным каналом.
   Кешированный снимок для допуска команды не используется. Проверяются подпись,
   соответствие ответу запроса, authority сервера, хеш и ревизия снимка.
3. По роли из свежего ответа повторно проверяется разрешение операции. Если старый
   сервер не передал `role_scope`, остаются ограничения подписанного допуска;
   серверная проверка активности отправителя всё равно выполняется при запросе снимка.
4. После успешной проверки формируются payload и подписанный конверт основной
   команды. Для изменений политики используется ревизия того же свежего снимка.
5. Команда отправляется, затем проверяется подписанный ответ сервера. Сервер
   сохраняет окончательную проверку прав: предварительная проверка на клиенте
   не отменяет серверную авторизацию и не устраняет гонку отзыва прав после проверки.

Запрос самого снимка является проверкой доступа и не вызывает рекурсивный запрос
другого снимка. Проверка охватывает общий административный API, включая чтение
списков; старое получение списка профилей переведено на этот API. Дополнительно
охвачены прежние пути создания профиля, изменения его состояния, выдачи приглашения
профиля и приглашения назначения.

## Отмена до отправки

При отсутствии локального допуска, неподтверждённом доступе, отказе сервера,
некорректном подписанном снимке или отсутствии разрешения роли основная команда
не подписывается и не отправляется.

В локальном журнале появляется `cancelled_local` с отображением **«Отменено локально»**,
операцией и причиной. В установочном журнале записывается `admin_cancelled_local`
с `before_send=true`. Отдельная команда отмены на сервер не отправляется: исходная
операция там не начиналась. Проверочный запрос к серверу может иметь собственный
результат отказа в журнале.

Неуспех после начала отправки основной команды не является локальной отменой.
Для подтверждённого серверного отказа сохраняется `failed`, для неизвестного
результата — предусмотренный существующим путём `unknown` и последующая сверка.

Параллельная команда изменения того же сервера отклоняется до выполнения своего
тела. Блокировка освобождается при успехе, ошибке или отмене проверки. Вложенный
запрос снимка не переводит родительскую команду в состояние «отправлена».

Первичная установка, вступление администратора, восстановление владельца по SSH,
погашение клиентского приглашения и синхронизация маршрутов обычного клиента
имеют собственные основания авторизации и не требуют заранее существующего
административного допуска. Их протоколы этим изменением не заменяются.

## Кнопки и состояние интерфейса

Дополнение: доступность после отказа пересчитывается по живому состоянию прав,
а привилегированный SSH позволяет получить допуск без отзыва других владельцев.
[Описание и проверки](ssh-administration-access-2026-10-15.md).

Экраны администрирования, настройки протоколов, комнат Jazz и сервера подписаны
на общее состояние команд репозитория. Их диалоги подключаются через `DialogScreens`.

На время активной команды изменения кнопки и доступные элементы ввода блокируются.
Фоновое чтение снимка не блокирует весь экран. Первый снимок и его ошибка
сохраняются в памяти процесса для выбранного сервера и допуска; повторный вход
использует их. Ручное обновление и проверка перед изменением всегда свежие.
Успешная выдача допуска через SSH сразу подтверждает права текущего сеанса.
Добавление нового сервера (на обзоре и во вкладке серверов) и навигация между
вкладками остаются доступными: эти действия не требуют допуска к опрашиваемому серверу.
Текстовые кнопки показывают текущий этап:

- **«Проверяем доступ…»**;
- **«Формируем команду…»**;
- **«Выполняем…»**.

После завершения восстанавливаются исходные подписи и доступность элементов.
В «Деталях пользователя» прогресс отображается только в «Настроить доступ»;
остальные действия блокируются без изменения подписей, включая промежутки
между командами настройки. [Описание изменения от 16 октября](admin-readiness-and-user-progress-2026-10-16.md).
Динамически созданные кнопки также получают блокировку. Обработчики представлений
отсоединяются при уничтожении экрана и закрытии диалога. Защита от параллельной
команды находится в репозитории и не зависит от активности экрана.

## Реализация

- `admin/AdminCommandControl.kt` — этапы, вложенные запросы и блокировка изменений;
- `admin/AdminRepository.kt` — живая проверка доступа, подготовка и журнал отмен;
- `admin/AdminCommandFeedback.kt` — блокировка элементов и подписи кнопок;
- `admin/AdminCommandsAdapter.kt` — отображение локальной отмены;
- `ui/DialogScreens.kt` — подключение обратной связи в диалогах.

Изменение не требует нового endpoint или обновления серверного ядра.

## Проверка

`:app:testDebugUnitTest :app:assembleDebug` — успешно, **350 JVM-тестов**,
включая `verifyCoreArtifacts` при сборке APK.

Добавлены сценарии:

- сервер отозвал права: отправлен только проверочный запрос, основная команда отсутствует;
- сервер понизил роль владельца до наблюдателя: изменение не отправлено;
- успешная проверка предшествует отправке изменения;
- ошибка вложенного проверочного запроса оставляет основную команду неотправленной;
- потеря ответа после отправки не классифицируется как локальная отмена;
- параллельное изменение отклоняется без выполнения тела второй команды;
- состояние занятости и блокировка снимаются при завершении.

Тест старого SSH-моста обновления дополнен ответом на новый проверочный запрос;
сверка той же операции после потери ACK по-прежнему проходит.

После подключения телефона dev-сборка установлена через `adb install -r` и успешно
запущена. По просьбе пользователя дальнейшую ручную приёмку выполняет он сам;
проверка этапов кнопок и локальной отмены на устройстве пока не подтверждена.
Серверные настройки и права пользователей не изменялись.
