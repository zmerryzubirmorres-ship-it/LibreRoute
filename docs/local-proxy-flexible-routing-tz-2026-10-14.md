# ТЗ: гибкая маршрутизация локального прокси

Дата: 2026-10-14. Проекты: LibreRoute-Android и LibreRoute-Core.

Статус: требования к реализации. Описанные ниже новые возможности пока не реализованы.

## 1. Цель и ожидаемый результат

Добавить два способа обработки запросов локального прокси:

1. **«Всё через туннель»** — все принятые прокси запросы передаются через выбранное серверное подключение.
2. **«По правилам маршрутизации»** — для каждого нового запроса выбирается прямой доступ, профиль zapret либо выбранное серверное подключение.

Один и тот же выбор действует для локального SOCKS5 на телефоне и раздачи SOCKS5/HTTP через «Раздача прокси / Хотспот». Список сайтов и профили zapret общие с существующим разделом настройки маршрутов. Повторно вводить списки для прокси не требуется.

Пример гибкого режима:

| Правило сайта | Путь запроса |
| --- | --- |
| `gosuslugi.ru` — напрямую | Клиент → прокси телефона → сайт |
| `youtube.com` — zapret, профиль «Видео» | Клиент → прокси телефона → локальный профиль «Видео» → сайт |
| `example.org` — через туннель | Клиент → прокси телефона → Jazz/Яндекс/другой выбранный канал → сервер → сайт |
| Сайт отсутствует в правилах | Путь определяет «Вне списков — через туннель» |

Имя профиля «Видео» приведено как пример пользовательского профиля; создавать его с выдуманными рабочими параметрами автоматически не требуется.

Под «напрямую» понимается соединение из телефона без туннеля LibreRoute и без обработки zapret. В режиме без VPN-службы оно использует маршрутизацию Android; если на телефоне работает сторонний VPN, прямое соединение может идти через него. Обещать обход стороннего VPN нельзя.

## 2. Текущее состояние и причины доработки

В текущей реализации:

- `LibreRouteProxyService` запускает Core с SOCKS5-входом, без Android TUN.
- `LocalProxyOptions.kt` при `proxyOnly = true` удаляет параметры TUN, правил сайтов, доменов и IP.
- `NativeProcessSupervisor` не формирует конфигурацию маршрутов для SOCKS5-входа.
- `client_features.go` в Core разрешает `site-routes-file` только для Android TUN.
- `runClient` передаёт SOCKS5-серверу один `TCPTunnel` как dialer. Выбора между direct/zapret/tunnel здесь нет.
- Правила гибридной маршрутизации в Core привязаны к `PacketTunnel`; требуется выделить общую часть выбора маршрута.
- `HotspotProxyBridge` принимает SOCKS5, HTTP и CONNECT и передаёт запросы в локальный SOCKS5 Core. Самостоятельно выбирать маршрут он не должен.
- При потере серверного транспорта текущий сервис останавливается. Для гибкого режима потребуется раздельное состояние локального прокси и доступности туннеля.
- Автономный zapret сейчас требует TUN и не предоставляет описываемый локальный прокси.

Изменение одной галочки без доработки Android и Core не решает задачу.

## 3. Объём работ и ограничения

### 3.1. Обязательный результат

Реализовать оба режима для TCP CONNECT через SOCKS5, HTTP-прокси и HTTP CONNECT, включая:

- доменные правила «Напрямую», «zapret», «Через туннель»;
- выбор конкретного профиля zapret для сайта;
- общий переключатель маршрута для сайтов вне списков;
- использование нескольких профилей zapret одновременно;
- раздачу того же поведения другим устройствам;
- сохранение выбора после поворота экрана, перезапуска и обновления;
- работу прямых и zapret-маршрутов при временной недоступности выбранного сервера;
- диагностику фактически выбранного пути;
- независимость решения от провайдера транспорта: Jazz, Яндекс и объединение каналов не должны требовать отдельных реализаций правил.

### 3.2. Что не входит в обязательную первую реализацию

- SOCKS5 UDP ASSOCIATE, передача QUIC через прокси и прозрачная маршрутизация точки доступа.
- Определение приложения на ноутбуке/ТВ или идентификация устройства по имени приложения.
- Перехват TLS, установка сертификата, анализ содержимого HTTPS.
- Автоматический подбор рабочих параметров zapret для каждого провайдера.
- Автоматический запуск VPN после установки приложения.
- Новые списки правил по пользователям или устройствам LAN.

Поддержка IPv6 должна быть определена явно: обязательный минимум сохраняет текущую поддержку доменных и IPv4-запросов. Для неподдерживаемого IPv6 возвращается корректная ошибка протокола. Нельзя принимать запрос и незаметно отправлять его другим путём. Расширение до IPv6 допускается отдельным этапом.

## 4. Интерфейс приложения

### 4.1. Расположение и точные подписи

В существующей группе настроек прокси сохранить:

- «Режим только прокси»;
- «Раздача прокси / Хотспот»;
- «SOCKS5-авторизация».

Добавить отдельный переключатель:

**«Использовать правила маршрутизации»**.

| Положение | Отображаемый режим | Пояснение |
| --- | --- | --- |
| Выключен | «Всё через туннель» | «Все запросы прокси идут через выбранное серверное подключение. Правила сайтов не применяются.» |
| Включён | «По правилам маршрутизации» | «Сайты идут напрямую, через zapret или через туннель согласно вашим правилам.» |

Переключатель не заменяет «Режим только прокси»: первый определяет путь запросов прокси, второй — запуск без VPN-службы.

Настройка действует и на раздаваемый прокси при активном VPN LibreRoute. Выбор режима прокси сам по себе не меняет обработку обычного трафика VPN.

### 4.2. Переход к общим правилам

При включённом гибком режиме показать действие **«Настроить маршруты сайтов»**. Оно открывает существующий экран маршрутов сразу на сайтах.

Показать текущее значение общего переключателя:

- «Вне списков — через туннель»;
- либо «Вне списков — напрямую».

Если это значение можно изменить прямо из настроек прокси, изменяется тот же общий параметр, который уже используется в экране маршрутов. Второго независимого значения не создавать.

В окне раздачи показывать адрес, порт, требование авторизации, режим прокси и состояние каждого доступного пути. Адрес не должен исчезать только из-за потери сервера, если локальный listener продолжает работать.

### 4.3. Ограничение правил приложений

Рядом с настройкой гибкого прокси показать пояснение:

> «Прокси использует правила сайтов. Правила приложений телефона действуют в VPN-режиме.»

Для раздачи добавить:

> «На других устройствах маршрут определяется по адресу сайта. Приложение, отправившее запрос, телефону неизвестно.»

Не показывать пользователю, что правило пакета YouTube автоматически управляет YouTube на ТВ. Для прокси должно существовать отдельное доменное правило сайта.

### 4.4. Применение изменений

В первой реализации изменение режима, правил, положения «Вне списков» и настроек профиля применяется после переподключения. Во время работы показать **«Изменения применятся после переподключения»** и действие **«Переподключить»**.

Показывать отдельно сохранённое значение и действующий режим, если они различаются. Не отображать новый режим как уже применённый.

При переподключении существующие TCP-соединения могут закрываться. Реализация обновления правил без переподключения допустима позже, с атомарной заменой снимка и сохранением маршрута уже открытых соединений.

### 4.5. Состояние экранов

Поворот экрана и возврат кнопкой «Назад» не сбрасывают:

- положение переключателей и открытое окно;
- введённые, но ещё не сохранённые логин/пароль;
- текущую вкладку, поиск, фильтр и позицию списка сайтов;
- сообщение о необходимости переподключения и индикатор подключения.

Открытие настроек не запускает серверные запросы и повторный полный обход установленных приложений.

## 5. Семантика выбора маршрута

### 5.1. Режим «Всё через туннель»

Любой разрешённый TCP-запрос прокси использует выбранное серверное подключение.

Правила сайтов, пакетов, автоматическое правило `ru.*`, профили zapret и переключатель «Вне списков — через туннель» на этот путь не влияют.

Если туннель недоступен, запрос завершается ошибкой. Переключаться на прямой доступ или zapret автоматически запрещено.

### 5.2. Режим «По правилам маршрутизации»

Обработка нового запроса:

1. Проверить авторизацию и корректность целевого адреса.
2. Привести доменное имя к общему каноническому виду.
3. Если правила сайтов включены, выбрать совпадающее правило по существующему общему механизму сопоставления.
4. Если совпадения нет либо правила сайтов отключены, применить «Вне списков — через туннель».
5. Открыть исходящее соединение строго через выбранный путь.
6. Зафиксировать этот путь до закрытия соединения.

| Результат правила | Реализация |
| --- | --- |
| `direct` | TCP-соединение из телефона без серверного туннеля LibreRoute и без zapret |
| `zapret` + ID профиля | SOCKS5 локального tpws, запущенного с указанным профилем |
| `tunnel` | Существующий dialer выбранного серверного подключения |
| Нет правила; «Вне списков» включён | `tunnel` |
| Нет правила; «Вне списков» выключен | `direct` |

Два выключенных списка правил не означают принудительный туннель: общий маршрут вне списков продолжает действовать.

### 5.3. Доменные имена и приоритет

Использовать общий matcher с VPN, а не писать второй с другой семантикой.

Обязательные свойства:

- регистр не учитывается; конечная точка DNS и IDN нормализуются;
- правило `example.org` применяется к самому домену и его поддоменам;
- оно не совпадает с `notexample.org` или `example.org.attacker.test`;
- более конкретный поддомен имеет приоритет над родительским доменом и зоной;
- правило `video.example.org → tunnel` побеждает `example.org → direct`;
- дубликаты и конфликтующие записи одного домена отклоняются при сохранении;
- порядок строк не должен менять результат.

Если текущий matcher отличается от этих требований, устранить различие в общем компоненте и проверить регрессию VPN.

### 5.4. IP-адрес вместо домена

Если SOCKS5-клиент передал IP, доменные правила применить достоверно нельзя. Не угадывать сайт по reverse DNS или общей истории DNS-кэша.

Для первой реализации запрос по IP следует общему маршруту «Вне списков». В интерфейсе справки рекомендовать SOCKS5 с разрешением имени через прокси, например `socks5h` в curl.

Старые отдельные параметры IP/domain split не должны незаметно менять этот алгоритм. Для гибкого прокси единственным источником правил служит общая конфигурация маршрутов сайтов; несовместимые старые параметры исключаются явно. Возможное подключение IP/CIDR-правил требует отдельной определённой таблицы приоритетов.

### 5.5. Правила пакетов `ru.*`

`ru.*` — префикс Android-пакета, а `.ru` — доменная зона. Это разные правила.

Автоматический прямой маршрут Android-пакетов `ru.*` остаётся частью правил приложений VPN. Он не применяется к запросам LAN и к чистому SOCKS5, в котором нет подтверждённого приложения-источника.

Правило сайта `ru → direct` применяется к прокси в гибком режиме. В режиме «Всё через туннель» оно игнорируется.

### 5.6. Отсутствие скрытого fallback

При ошибке выбранного пути запрос завершается ошибкой этого пути:

- сбой туннеля не открывает сайт напрямую;
- сбой zapret не отправляет запрос на сервер;
- сбой прямого соединения не переключает его в туннель;
- удалённый/невалидный профиль не заменяется «Стандартным» незаметно.

Любые будущие цепочки резервирования должны быть отдельной явно включаемой функцией с описанным порядком. В данное ТЗ они не входят.

## 6. DNS и протоколы прокси

### 6.1. Домен нужно сохранить до выбора пути

Имя назначения из SOCKS5 DOMAIN, HTTP absolute-form и HTTP CONNECT должно доходить до маршрутизатора Core без предварительного преобразования в IP на Java-мосте.

Маршрут выбирается до DNS-разрешения. Для `tunnel` разрешение выполняется через механизм туннеля; для `direct` — через локальный механизм Android; для `zapret` домен передаётся локальному DPI-dialer.

Не выполнять предварительный локальный DNS-запрос для домена, который должен идти через туннель. Кэш маршрутов не должен смешивать решения по имени, IP и разным версиям конфигурации.

Существующая настройка DoH применяется по определённой политике каждого пути. Запрос к DoH не должен рекурсивно проходить через тот же пользовательский прокси. До реализации зафиксировать таблицу DNS-путей в техническом описании; обязательные тесты должны доказать отсутствие локального разрешения для туннельного домена.

### 6.2. HTTP и CONNECT

- HTTP-прокси выбирает путь по host/port из абсолютного URL; при разрешённом origin-form — из корректного Host.
- Несогласованные или неоднозначные целевые адреса отклоняются, а не выбираются произвольно.
- Заголовки `Proxy-Authorization` и `Proxy-Connection` не передаются конечному сайту.
- Обычный HTTP сохраняет текущую модель одного запроса на соединение с `Connection: close`.
- CONNECT выбирает путь по целевому host/port и затем передаёт TCP в обе стороны.
- Ответ об успешном соединении возвращается после реального открытия выбранного исходящего пути.
- HTTPS не расшифровывается; решение не зависит от URL-пути внутри HTTPS.

### 6.3. Ошибки и передача данных

Возвращать корректный отказ SOCKS5 либо HTTP 400/407/502/503 в зависимости от причины и стадии обработки. Нельзя возвращать «соединение установлено», а затем скрывать ошибку выбора маршрута.

Реле должно поддерживать двустороннюю передачу, длительные CONNECT/WebSocket-соединения и корректное завершение направлений. Тайм-аут handshake после установления соединения снимается. Half-close проверяется на полном пути, а не только на Java-мосте.

UDP и QUIC через этот TCP-прокси не обещать. Параметр профиля «блокировать QUIC» не означает появление поддержки UDP ASSOCIATE.

## 7. Изменения архитектуры Core

### 7.1. Общий механизм маршрутизации

Выделить общий компонент выбора и исполнения маршрута, доступный PacketTunnel и SOCKS5-входу. Разделить:

- сопоставление сайта с действием;
- подготовленные direct/zapret/tunnel dialer;
- метаданные входа: домен, порт, тип источника;
- получение Android UID, которое остаётся адаптером TUN.

Чистый прокси не должен вызывать текущий `AppRouteServer` с выдуманным адресом `26.26.26.1`, приписывать запрос UID LibreRoute или считать отсутствие UID ошибкой, принудительно отправляющей всё в туннель.

В первой реализации правила приложений для всех proxy-входов отключены независимо от наличия параллельного VPN. Это обеспечивает одинаковое поведение локального клиента и LAN. TUN продолжает применять свои правила приложений.

### 7.2. SOCKS5-вход

Сохранить существующий интерфейс dialer либо расширить его адаптером: handshake и авторизация не должны знать список провайдеров или самостоятельно выбирать direct/zapret/tunnel.

В гибком режиме передавать SOCKS5-серверу маршрутизирующий dialer; в режиме «Всё через туннель» — туннельный dialer. Аналогичный выбор должен применяться к локальному SOCKS5-listener, запущенному вместе с Android TUN.

LAN-мост и локальный SOCKS5 не должны принимать решение дважды. Нельзя создавать цепочку «мост → прокси → тот же мост» или дополнительный серверный туннель ради маршрутизации.

### 7.3. Конфигурация и совместимость

Добавить явный параметр режима прокси, например `proxy-routing-mode=all_tunnel|rules`. Окончательное имя согласовать с существующим форматом флагов; значения и семантика должны быть стабильными.

Для гибкого режима разрешить конфигурацию сайтов на SOCKS5-входе. Проверка конфигурации должна учитывать тип входа: поля TUN и app_socket не допускаются в конфигурации чистого прокси.

Отдельно управлять маршрутизацией TUN и SOCKS5 в совместном запуске. Режим «Всё через туннель» у прокси не должен отключать маршруты самого VPN.

Заранее валидировать профиль, порт, адрес, режим и ссылки на профили. Некорректная конфигурация не должна приводить к запуску другого режима по умолчанию.

## 8. Изменения Android

### 8.1. Подготовка и запуск

`NativeProcessSupervisor` должен готовить снимок правил для гибкого SOCKS5 так же согласованно, как для TUN, но без TUN-аргументов и app_socket.

`LocalProxyOptions` должен различать несовместимые параметры TUN и необходимую конфигурацию сайтов. В гибком режиме нельзя продолжать безусловно удалять `site-routes-file`.

Запускать каждый используемый профиль zapret один раз на сессию. Если один профиль нужен TUN и SOCKS5, не запускать два одинаковых процесса без необходимости. Неиспользуемые профили не запускать.

Проверять готовность профиля до приёма запросов, закрывать процессы, временные файлы и сокеты при отмене/смене подключения. Логин и пароль SOCKS5 должны совпадать во всех входах и внутренних проверках.

### 8.2. Готовность и потеря связи

Разделить как минимум состояния:

- локальный listener остановлен/запускается/готов;
- серверный туннель подключается/готов/недоступен;
- готовность используемых профилей zapret;
- LAN-раздача выключена/готова/ошибка привязки порта;
- сохранённые изменения ожидают переподключения.

В гибком режиме локальный прокси может быть готов при недоступном туннеле: direct и готовые zapret-маршруты обслуживаются, tunnel-запросы получают отказ.

Это касается и старта при недоступном выбранном сервере: нельзя бесконечно ждать peer readiness, блокируя работоспособные локальные пути. Подготовку локального listener, профилей и удалённого транспорта нужно разделить.

Восстановление серверного транспорта не должно требовать повторного ввода адреса прокси на ноутбуке/ТВ. Автоматическое восстановление использует существующий механизм соединения, без параллельных дублирующих запусков.

Команда пользователя «Отключить» полностью останавливает все пути и LAN-раздачу. Частичная доступность после сбоя сервера не должна превращаться в скрытую работу после явного отключения.

### 8.3. VPN и маршрутизация Android

«Режим только прокси» с серверным подключением не создаёт TUN и не запрашивает VPN-разрешение. Сторонний VPN не останавливается.

При совместной работе с VPN LibreRoute direct/zapret-сокеты, DNS и служебные соединения должны быть защищены от повторного попадания в собственный TUN существующим механизмом защиты/привязки сокетов. Проверить защиту, а не считать её автоматически работающей после выделения нового dialer.

## 9. Сохранение, начальные настройки и миграция

Добавить постоянный enum настройки режима прокси; галочка является только UI-представлением. Не хранить его в поле режима VPN или положения «Вне списков».

Для новой установки:

- «Использовать правила маршрутизации» включено;
- «Вне списков — через туннель» выключено согласно принятой преднастройке;
- применяется существующий встроенный набор `routing-defaults.json`;
- «Режим только прокси» и LAN-раздача автоматически не включаются;
- правила приложений из набора применяются к VPN, правила сайтов — к гибкому прокси.

Текущий встроенный набор содержит 107 правил приложений и 646 правил сайтов с прямым доступом. Поэтому наличие назначения zapret у приложения YouTube само по себе не создаёт zapret-маршрут YouTube в прокси. Нужные домены пользователь добавляет в «Маршруты сайтов»; автоматически выводить домены из имени Android-пакета нельзя. Отдельные проверенные доменные пресеты допустимы как последующая доработка с явным составом.

Для обновления существующей установки:

- прежнее поведение прокси сохранить как «Всё через туннель»;
- сохранённые сайты, профили и переключатель «Вне списков» не перезаписывать;
- показать доступность новой настройки без автоматического изменения сетевого пути;
- однократно записать результат миграции до запуска фоновых служб;
- повторное обновление не должно сбрасывать выбор пользователя.

Отличать новую установку от миграции по принятому в приложении механизму версии настроек/инициализации. Не определять новизну по пустому списку сайтов. Если прежний статус определить нельзя, выбирать совместимое «Всё через туннель».

Режим включается в экспорт/импорт настроек. Старый backup без нового поля восстанавливает совместимое «Всё через туннель», новый сохраняет выбранное значение. Экспорт не содержит runtime-портов, UID и временных путей.

## 10. Работа без удалённого сервера

Обязательный этап данного ТЗ — гибкий прокси с выбранным серверным профилем, включая временную недоступность этого сервера.

Отдельный следующий этап — полноценный запуск локального прокси с выбранным «Прямой обход DPI · zapret» без серверного профиля. Его нельзя объявлять готовым после первого этапа: текущие Android и Core требуют для такого подключения TUN.

Для этого следующего этапа зафиксировать семантику заранее:

- `direct` идёт напрямую;
- `zapret` использует назначенный профиль;
- `tunnel` и общий маршрут через туннель используют общий профиль автономного zapret, как в существующем автономном режиме;
- интерфейс явно пишет, что удалённого сервера нет;
- вариант «Всё через туннель» здесь недоступен с пояснением, а не выдаётся за настоящий серверный туннель;
- SOCKS5 запускается без запроса VPN-разрешения.

Эту возможность принимать отдельной строкой плана; первый этап не должен менять существующий автономный TUN-zapret.

## 11. Диагностика и производительность

Для нового запроса должны быть доступны: вход local/LAN, режим, версия снимка правил, выбранное действие, ID профиля при zapret, основание решения и причина отказа. Пользователь должен отличать недоступность туннеля от отказа direct или профиля zapret.

Подробный журнал с доменами включается отдельно. В обычном журнале не писать полный URL, содержимое запросов, пароли и токены; ограничить повторяющиеся сообщения. Показывать агрегированные счётчики direct/zapret/tunnel и ошибок по путям в диагностике сессии.

Внутренний ping сервера должен проверять именно tunnel-dialer. Проверка direct-сайта через гибкий прокси не доказывает, что сервер подключён.

Загрузку и валидацию правил выполнять при подготовке снимка, а не для каждого пакета. На запрос не нужны чтение SharedPreferences, обращение к PackageManager, опрос сервера или полный перебор профилей.

Допускается одно дополнительное локальное обращение к tpws для zapret. Для direct и tunnel добавлять лишний Java TCP-мост относительно текущего локального SOCKS5 нельзя.

На одном стенде сравнить режим «Всё через туннель» до/после: медианная скорость передачи не должна ухудшаться более чем на 5% в серии из пяти одинаковых запусков. Сопоставлять одинаковые транспорт, объём, устройство и сетевые условия; нестабильность внешнего канала отделять от измерения локальных накладных расходов. Если разброс превышает измеряемую разницу, вывод о регрессии не делать по одному прогону.

## 12. План реализации

1. Общий matcher/маршрутизирующий dialer Core, конфигурация и модульные тесты.
2. SOCKS5-вход с режимами all_tunnel/rules, реальные TCP-тесты всех трёх путей и авторизации.
3. Подготовка конфигурации Android, запуск профилей, состояния локального listener и удалённого транспорта.
4. Настройка, пояснения, миграция и backup; применение выбора к SOCKS5 вместе с TUN.
5. LAN-мост SOCKS5/HTTP/CONNECT, домены и диагностика фактического пути.
6. Регрессия VPN и контрольные проверки телефона/второго устройства.
7. Отдельное расширение: автономный гибкий прокси без серверного профиля.

Каждый этап завершать конкретными изменениями и проверкой его поведения. Не подменять реализацию одним изменением UI или снятием проверки флага в Core.

## 13. Приёмочные сценарии

### 13.1. Автоматизированные проверки

| № | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| A1 | Всё через туннель; сайт помечен direct/zapret | Используется только tunnel-dialer |
| A2 | Гибкий режим, по одному домену на каждый путь | Запрос достигает соответствующего тестового endpoint; остальные dialer не вызваны |
| A3 | Два сайта с разными профилями zapret | Используются два разных назначенных локальных endpoint |
| A4 | Сайт вне списков, оба положения общего переключателя | Direct при выключенном, tunnel при включённом |
| A5 | Список сайтов выключен, в том числе при обоих выключенных списках | Действует общий маршрут вне списков |
| A6 | Поддомен, зона, IDN, регистр, похожий чужой домен | Детерминированный выбор по правилам раздела 5.3 |
| A7 | SOCKS5 DOMAIN и запрос по IP | Первый использует доменное правило, второй — общий маршрут |
| A8 | Tunnel-домен и наблюдаемый локальный DNS-resolver | Предварительного локального DNS-запроса нет |
| A9 | Потеря сервера во время работы и недоступный сервер при старте | Direct/zapret доступны; tunnel-запрос отклонён без fallback |
| A10 | Ошибка выбранного профиля либо прямого пути | Нет обращения к другим путям |
| A11 | Локальный SOCKS5 и LAN SOCKS5/HTTP/CONNECT с одним доменом | Одинаковый путь при одинаковой конфигурации |
| A12 | Верный/неверный пароль, клиент не предлагает требуемую авторизацию | Успех только при корректном handshake; секреты не попадают на сайт |
| A13 | Большой обмен в обе стороны, half-close, idle CONNECT, отмена | Нет обрезания ответа, преждевременного тайм-аута и оставшихся listener |
| A14 | Снимок настроек изменён во время сессии | До переподключения действует прежний снимок; UI показывает ожидающее изменение |
| A15 | Новая установка, миграция, старый/новый backup | Начальные значения и сохранённые настройки соответствуют разделу 9 |
| A16 | Одновременно TUN и SOCKS5 с разными режимами | Настройка прокси не меняет маршруты VPN; proxy-вход не получает выдуманный UID |
| A17 | Отмена запуска, повторное подключение, явное отключение | Нет дублирующих процессов, временных файлов и незакрытой LAN-раздачи |

### 13.2. Проверки на телефоне и втором устройстве

Проверить одним набором доменов:

1. Серверный Jazz и отдельно Яндекс: локальный клиент прокси использует все три пути в гибком режиме.
2. На ноутбуке/ТВ через раздачу повторяется тот же результат; идентификация Android-приложения не используется.
3. «Всё через туннель» отправляет все контрольные сайты через сервер, включая `.ru`.
4. Выключение «Вне списков — через туннель» меняет только запросы вне правил в гибком режиме.
5. Потеря сервера, его восстановление и смена Wi-Fi/мобильной сети отражаются корректно; доступные локальные пути работают без перенастройки клиента LAN.
6. На чистом серверном proxy-only запуске не появляется запрос VPN-разрешения; работающий сторонний VPN не отключается.
7. В режиме VPN LibreRoute direct-запросы не зацикливаются через собственный TUN; существующие правила приложений сохраняют поведение.
8. Поворот экрана, системная «Назад», перезапуск приложения и повторное открытие настроек сохраняют состояние.

Доказывать путь журналом маршрутизатора и наблюдением контрольных endpoint/серверных соединений. Одного открытия сайта, значка подключения или проверки внешнего IP для zapret недостаточно: direct и zapret обычно имеют одинаковый внешний IP.

### 13.3. Условие завершения

Обязательный этап принят, когда оба режима работают через локальный и LAN-прокси, все три пути подтверждены фактическими запросами, отсутствует скрытый fallback, пройдены миграция/регрессия VPN и зафиксированы версии APK/Core с результатами проверок.

Непроведённые живые проверки перечислить отдельно. Их нельзя заменять фразой «всё работает» на основании одних unit-тестов. Поддержка автономного proxy-only zapret принимается отдельно после этапа 7.

## 14. Основные точки изменения

Android:

- `service/LocalProxyOptions.kt`, `service/NativeProcessSupervisor.kt` — параметры и снимок маршрутов;
- `service/LibreRouteProxyService.kt`, `service/SocksVpnService.kt` — запуск, доступность путей и остановка;
- `service/HotspotProxyBridge.kt`, `service/ProxySharing.kt` — сохранение домена, раздача и готовность;
- `service/ProxyConnectivityProbe.kt` — различение проверки прокси и удалённого туннеля;
- `util/AppSettings.kt`, `util/ConfigBackupManager.kt` — настройка и миграция;
- `ui/SettingsActivity.kt`, `ui/SettingsViewModel.kt`, ресурсы — переключатель и фактическое состояние;
- общие модели сайтов/профилей — повторное использование без копии пользовательских списков.

Core:

- `client_features.go`, `main.go` — режим и допустимые конфигурации входов;
- `socks5/socks5.go` — подключение нужного dialer, завершение передачи и ошибки;
- `site_routing.go`, `tunnel/site_routing.go`, `tunnel/policy` — общий выбор маршрута;
- `directdpi` — использование профилей и DNS без рекурсии;
- Android TUN-адаптер — защита исходящих сокетов и сохранение прежней маршрутизации;
- `direct_dpi.go` — только для отдельного этапа автономного SOCKS5.

Файлы перечислены как ориентиры по состоянию на дату ТЗ. Итоговая структура может изменяться при выделении общего компонента, если сохраняются описанные контракты и приёмочные сценарии.
