# Проверка настроек прокси — 2026-10-14

Проверялась группа «Прокси»: «Раздача прокси / Хотспот», «SOCKS5-авторизация», «Режим только прокси». Исходная установленная версия — 1.2.35. В ней обнаружены функциональные ошибки. Исправления включены в 1.2.36; Core остаётся 1.2.44.

## Обнаруженные ошибки

1. `HotspotProxyBridge.handleClient` запускал два потока передачи и возвращался. `finally` рабочего потока сразу закрывал клиентский сокет. Подключение принималось, но данные обрывались. На TCP-стенде воспроизведён обрыв SOCKS5-передачи.
2. HTTP-прокси отправлял конечному серверу абсолютный URL вместо пути и не удалял `Proxy-Authorization`. На стенде сервер получил оба неверных элемента. Теперь запрос имеет origin-form, заголовки авторизации прокси удаляются, `Connection: close` явно ограничивает обычное HTTP-соединение одним запросом. CONNECT остаётся двусторонним TCP-реле.
3. Отдельный поток копирования закрывал оба сокета при EOF, обрезая ответ после полузакрытия загрузки. Исправлена Java-раздача: полузакрытие сохраняет обратное направление. Это проверка Java-моста с изолированным SOCKS-backend, а не доказательство поддержки half-close всем удалённым транспортом Core.
4. При отключённой авторизации мост выбирал метод `NO AUTH`, даже если клиент его не предлагал. Теперь такой запрос отклоняется.
5. В VPN-режиме адрес SOCKS5 передавался ядру, а логин и пароль оставались только в Android Intent. Общий `NativeProcessSupervisor` теперь формирует адрес и авторизацию из одной сессии для UI, плитки, автозапуска и переподключений. Проверка связи и пинг выполняют SOCKS5-авторизацию явно; глобальный Java Authenticator не изменяется.
6. В режиме «только прокси» оставались параметры раздельного туннелирования, которые Core разрешает только для Android TUN. Они удаляются вместе с TUN-параметрами во всех поддержанных формах флагов. Пустой список приложений TUN больше не блокирует прокси. Основной экран больше не запрашивает разрешение VPN для серверного SOCKS5-подключения.
7. Сервис прокси использовал короткое ожидание 20 секунд вместо общего окна готовности, мог повторно запускаться во время подключения и оставаться активным при переключении профиля или отмене подготовки. Добавлены учёт запуска, отмена, общий контроль готовности и остановка при потере транспорта; состояние «подключено» выставляется после готовности ядра.
8. Переключатель раздачи запускал мост без работающего Core, в том числе в автономном zapret. Теперь нужен готовый SOCKS5-endpoint. При изменении авторизации или учётных данных раздача прекращается до переподключения. Экран явно показывает состояние, локальный адрес и необходимость переподключения.
9. Определение LAN-адреса пропускало сети 10/8 и часть 172.16/12 и подставляло вымышленный 192.168.43.1. Теперь учитываются все RFC1918-сети; при отсутствии LAN отображается пояснение, копирование несуществующего адреса отключено.

## Проверки

Выполняются настоящие TCP-соединения через производственный `HotspotProxyBridge` к изолированному SOCKS5-backend. Ключи, документы и серверы пользователя не используются.

Первый прогон: 10 тестов, 5 ошибок. Включал 7 новых сетевых и 3 существующих теста upstream-авторизации. Одна ошибка HTTP-авторизации также связана с Android Base64-заглушкой JVM; декодирование переведено на стандартный Java Base64, доступный с минимального Android API проекта. Этот результат сам по себе не доказывает ошибку Base64 на телефоне.

Контрольный набор:

- SOCKS5 с паролем, неверным паролем и неподдерживаемым методом;
- HTTP без пароля, нормализация пути и удаление служебных учётных данных;
- HTTP CONNECT с авторизацией и обменом данными в обе стороны;
- запрет запуска защищённой раздачи с пустыми учётными данными;
- ответ 128 КиБ после half-close на Java-мосте;
- остановка listener и активных TCP-реле;
- авторизованный SOCKS5-handshake внутренней проверки связи без глобального Authenticator;
- параметры запуска VPN/SOCKS5, удаление устаревших параметров, предел 255 байт UTF-8;
- готовность и замена сессии, политика включения раздачи и определение LAN-сети;
- существующие проверки готовности транспорта.

Контрольный прогон: 29 тестов прошли без ошибок (`HotspotProxyBridgeIntegrationTest`, `HotspotProxyAuthenticationTest`, `LocalProxyOptionsTest`, `NativeTransportReadinessTest`). Debug APK собран успешно. Журнал: `.diagnostics/proxy-final-tests-and-debug-20261014.log`.

В окнах раздачи и авторизации добавлена прокрутка; окна открываются развёрнутыми, чтобы кнопки оставались доступны в горизонтальном положении.

На изолированном эмуляторе проверены: статус раздачи без Core, отсутствие вымышленного локального SOCKS5-адреса, сохранение окна и черновика авторизации при повороте, сохранение логина и переключателя режима. Кнопка сохранения доступна в горизонтальном положении после скрытия клавиатуры. Квитанция: `.diagnostics/proxy-settings-ui-20261014/ui-receipt.json`. Подключения к провайдерам не запускались.

Отдельно: `go test ./socks5 -count=1` в Core прошёл. Ядро не изменялось.

Локальные журналы: `.diagnostics/proxy-baseline-tests-20261014.log`, `.diagnostics/proxy-fixed-tests-20261014.log`, `.diagnostics/proxy-core-socks-tests-20261014.log`. Исходный XML неуспешных тестов сохранён в `.diagnostics/proxy-baseline-20261014/integration.xml`.

## Границы проверки

Результат тестов моста не заменяет живую проверку всего пути телефон → Jazz/Яндекс → сервер → сайт. Ещё требуется проверить на телефоне с реальным сервером оба режима (VPN и только прокси), доступ с другого устройства LAN, верный/неверный пароль, смену режима и восстановление после смены сети. Через USB пользовательский интерфейс телефона автоматически не переключался.

SOCKS5-раздача обслуживает TCP CONNECT. Это не прозрачная раздача всего трафика точки доступа и не SOCKS5 UDP ASSOCIATE. Другое устройство должно явно использовать SOCKS5 или HTTP-прокси телефона. Режим zapret остаётся локальным Android TUN и не создаёт SOCKS5-listener.
